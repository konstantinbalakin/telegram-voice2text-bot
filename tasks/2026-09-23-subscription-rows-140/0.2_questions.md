# Вопросы к Константину (issue #140 + «на новую подписку — отдельная строка»)

## Контекст находок (по коду main и прод-БД)

1. Полного UNIQUE(user_id) в прод-БД **нет**. Есть partial unique index `ix_user_subscriptions_unique_active ON user_subscriptions(user_id) WHERE status='active'` (миграция e7a1b2c3d4f5). SQLite сообщает о его нарушении как `UNIQUE constraint failed: user_subscriptions.user_id` — это и есть ошибка из логов.
2. Код уже рассчитан на «историю строк»: `SubscriptionService.create_subscription` деактивирует активную и вставляет новую строку. Падение происходит, когда у юзера строка со статусом `active`, но `expires_at <= now` (истекла по времени, но крон `check_expired_subscriptions` ещё не перекрасил в `expired`): `get_active_subscription` фильтрует по `expires_at > now`, не находит строку → деактивации нет → INSERT новой `active` → нарушение partial index.
3. Итого под желаемую «отдельная строка на подписку» схема почти готова; нужен фикс выборки «деактивировать все active-строки юзера независимо от expires_at» + страховки.

## Вопросы и ответы

### В1. Расчёт expires_at новой строки при покупке поверх действующей подписки (того же тира)
Варианты: (а) stacking: `max(now, старая.expires_at) + период` — оплаченные дни не сгорают; (б) с нуля: `now + период`.

**Ответ К. (2026-09-23):** (а) Stacking — оплаченные дни не сгорают.

### В2. Покупка другого тира поверх активного
Варианты: немедленный переход (старая → cancelled, новая с now+период), stacking только тот же тир; или stacking для любого тира.

**Ответ К. (2026-09-23):** Stacking для любого тира — да.

### В3. Partial unique index `ix_user_subscriptions_unique_active`
Оставлять ли как страховку БД-уровня (одна active-строка на юзера)?

**Ответ К. (2026-09-23):** Нет — при stacking у юзера могут быть одновременно 2 активных подписки (текущая ещё не кончилась + куплена новая). Index убрать. ⟹ следствие: `get_active_subscription`/`get_active_subscription_with_tier` (сейчас fail-fast `scalar_one_or_none` на дубли) должны перейти на множественный выбор с детерминированной семантикой (см. дизайн).

### В4. Reconciliation-скрипт для сгоревших платежей
**Ответ К. (2026-09-23):** Не нужен, всё компенсировано вручную.

### В5. Сопутствующее из issue (enum ABANDONED + тест матчинга pending)
**Ответ К. (2026-09-23):** Да, включить в этот же PR.

### В6. Статус старой строки при замене (`replaced` vs `cancelled`)
Не задан в пакете clarify (лимит 5 вопросов) — вынесен в дизайн: предложение там — без нового статуса, старая строка просто «доезжает» свой срок (при stacking ничего деактивировать не нужно).

## Открытый вопрос для дизайна (В7)

### В7–В10. Пакет после исследования лучших практик (2026-09-23, вторая итерация)

После разбора практик Apple/Google/Stripe/Spotify (`0.2a_best_practices.md`) вопрос «чей лимит при параллельных активных» снят — принята модель очереди.

**Ответы К.:**
- **В7 Модель**: очередь — активная подписка одна; новая покупка при активной → строка `queued`, стартует после окончания текущей. Отдельно продумать, кто переключает статусы (ответ в дизайне: расширение существующего крона `check_expired_subscriptions`).
- **В8 Апгрейд** (более высокий тир): вступает сразу + перенос остатка дней старой подписки в новую (аналог Google `WITH_TIME_PRORATION`).
- **В9 UX**: перед инвойсом — сообщение с датами («текущая до NN, новая с MM»), кнопки «Оплатить»/«Отмена», подсказка «нужно добрать минут на сегодня → пакеты минут».
- **В10 Даунгрейд**: применяется в конце текущего периода (механика `next_subscription_tier_id` уже есть), апгрейд — сразу. Уровень тира сравнивается по `display_order`.
