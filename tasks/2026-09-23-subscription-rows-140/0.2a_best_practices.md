# Лучшие практики подписок в популярных сервисах (исследование к #140)

Дата: 2026-09-23. Источники: docs.stripe.com (prorations, change-price), developer.apple.com (Auto-renewable Subscriptions), revenuecat.com (Managing Subscriptions), Qonversion, support.spotify.com, support.google.com.

## Общий принцип мейнстрима

Ни один крупный сервис не держит у клиента **двух активных подписок одновременно**. Активная ровно одна; всё остальное — правила перехода:

- **Апгрейд** (на более дорогой/высокий уровень) — вступает **немедленно**, с пересчётом (proration): Apple возвращает prorated-разницу, Google предлагает режимы (WITH_TIME_PRORATION: остаток времени старой подписки сдвигает дату первого списания новой; CHARGE_PRORATED_PRICE: доплачивается только разница за остаток периода), Stripe сразу инвойсит prorated-разницу.
- **Даунгрейд** — вступает **в конце текущего периода** (Apple, Google, Stripe best practice): «The subscription continues until the next renewal date, then is renewed at the lower level and price».
- **Покупка той же подписки при активной** — это продление: новая дата списания сдвигается (у Spotify prepaid/gift — накопление до 18 месяцев; YouTube/Netflix gift-коды аналогично). Двух параллельных подписок не возникает.

## Конкретные примеры

- **Apple App Store**: апгрейд immediate + refund prorated; даунгрейд — со следующего renewal. Если длительности разные — новая подписка с даты следующего renewal.
- **Google Play**: апгрейд immediate (рекомендуемый режим CHARGE_PRORATED_PRICE — доплата разницы, дата renewal сохраняется); даунгрейд — в конце периода.
- **Stripe**: `proration_behavior=always_invoice` (сразу списать разницу) для апгрейда; для даунгрейда — `pending_plan`/schedule на конец периода.
- **Spotify**: смена плана — «Стоимость новой подписки будет списана в день, когда закончится действие предыдущего тарифного плана. Этот день станет новой датой списания» (т.е. queued-переход). Продление вперёд — только через gift/prepaid, максимум 18 месяцев.

## UX-паттерн подтверждения

Крупные сервисы при смене плана показывают экран с датами и суммой до подтверждения («новая подписка начнётся тогда-то», «доплата составит столько-то»). Боту соответствует: перед выставлением инвойса — сообщение с условиями и кнопками подтверждения.

## Выводы для v2t-бота

1. Правильная модель — **последовательные строки** (очередь), а не параллельные активные: «новая подписка начнёт действовать после окончания текущей». Это снимает вопрос «чей daily_limit при двух активных» — активная всегда одна.
2. Для «докупить минуты сегодня» у бота уже есть правильный механизм — **пакеты минут**; подпиской это решать не надо, но стоит подсказывать пользователю.
3. Частичная проблема proration: у бота ручные платежи (ЮKassa/Stars), автосписаний нет — «доплата разницы» реализуемо только как «перенос остатка дней». Проще всего: при апгрейде остаток дней старой подписки приплюсовывается к новой (time-credit вместо money-proration, как Google WITH_TIME_PRORATION).
