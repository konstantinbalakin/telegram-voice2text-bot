# Дизайн: история подписок, очередь и правила перехода (#140)

Статус: draft → на ревью Константина
Дата: 2026-09-23
Входные данные: issue #140, ответы В1–В10 (`0.2_questions.md`), исследование практик (`0.2a_best_practices.md`)

## 1. Цель

Повторная покупка подписки (продление/смена тира) больше не падает с `UNIQUE constraint failed` и не сжигает платёж. Каждая покупка — отдельная строка в `user_subscriptions` (история). Модель — «очередь»: активная подписка одна.

## 2. Модель статусов

`SubscriptionStatus` (src/services/payments/base.py:20) пополняется:

| статус | смысл |
|---|---|
| `active` | действует сейчас, `expires_at > now` |
| `queued` | оплачена, ждёт окончания текущей active |
| `expired` | закончилась |
| `cancelled` | отменена пользователем / заменена |
| `replaced` | (опционально, см. §7) заменена апгрейдом |

Инвариант: `COUNT(status='active') <= 1` на пользователя, `COUNT(status='queued') <= 1`.

## 3. Сценарии покупки (PaymentService._activate_subscription → SubscriptionService)

### 3.1 Нет активной подписки (или истекла)
Как сейчас: INSERT `active`, `expires_at = now + период`.

### 3.2 Продление того же тира при активной
1. INSERT новой строки `status='queued'`.
2. `started_at = started_at_next = текущая.expires_at`, `expires_at = started_at + период`.
3. Partial unique index `ix_user_subscriptions_unique_active` остаётся — queued не попадает под WHERE status='active'.
4. Кнопка покупки (UX): «Текущая подписка действует до {дата}. Новая начнётся {дата} и закончится {дата}. Продолжить?» [Оплатить] [Отмена]. Если лимит на сегодня исчерпан — подсказка про пакеты минут.

### 3.3 Апгрейд (более высокий тир по `display_order`) при активной
1. Старая: `status='replaced'` (или `cancelled`), `updated_at`.
2. Новая строка `active`: `started_at = now`, `expires_at = now + период + остаток_дней_старой`, где `остаток_дней = (старая.expires_at - now)` полностью (дни+часы) переносится.
3. UX: «Апгрейд с {old} → {new}: новый лимит действует сразу, окончание новой подписки {дата} (включая остаток {N} дн. старой)».

### 3.4 Даунгрейд при активной
1. Покупка оплачивается, но новая строка создаётся только «виртуально» через существующий механизм `next_subscription_tier_id` на текущей active-строке.
2. Если уже есть queued-строка — она заменяется (обновляется её tier_id/период) либо отменяется и создаётся новая. Механика: перед созданием queued-строки существующая queued отменяется (`cancelled`), т.к. оплачена она быть ещё не может (оплата идёт после подтверждения, до INSERT).
3. UX: «С {дата окончания текущей} подписка станет {tier}: {лимит} мин/день».

### 3.5 Пограничный случай: истекла по времени, но статус ещё active (первопричина бага)
В `create_subscription` сначала деактивировать **все** строки со статусом `active` у юзера независимо от `expires_at` (метод `deactivate_all_active(user_id)`), затем INSERT. Это устраняет IntegrityError навсегда, даже если крон запаздывает.

### 3.6 Компенсация
Прошлые сгоревшие платежи компенсированы вручную — в код не выносим (В4).

## 4. Активация очереди (кто переключает)

Расширяем существующий крон `SubscriptionService.check_expired_subscriptions` (уже помечает expired):
1. Помечает expired: все `active` с `expires_at <= now`.
2. Активирует очередь: для юзеров, у которых нет active, но есть `queued` — самая ранняя по `started_at` queued становится `active`, её `started_at` = факт. истечения (не пересчитывая expires_at — период отсчитывается от планового старта? — см. вопрос Д1).
3. Альтернатива ленивой активации: `get_active_subscription` при отсутствии active проверяет queued с `started_at <= now` и активирует её. Решение — гибрид: крон (основной) + ленивая проверка (страховка).

## 4а. Идемпотентность выдачи

`handle_successful_payment` уже скипает по `provider_transaction_id` — сохранить. Дополнительно: INSERT строки подписки и mark_completed покупки должны происходить в одной транзакции сессии (сейчас `_activate_subscription` и mark_completed в разных сессиях — риск «подписка выдана, покупка pending» при падении между ними; идемпотентность по transaction_id скипнет повтор, но purchase останется pending навсегда). Решение: объединить в один unit of work (одна сессия: activate + mark_completed), затем коммит.

## 5. Схема БД / миграция

1. Новая миграция Alembic (head на main — b1c2d3e4f5a6):
   - ничего не удаляем; частичный unique index на active — остаётся;
   - BACKFILL не нужен (queued появятся только новыми покупками);
   - в models.py `__table_args__` — без изменений.
2. `PurchaseStatus`: добавить `ABANDONED = "abandoned"` (сопутствующее из issue, В5).
3. `find_pending_purchase` — уже матчит только `PENDING` (проверено кодом), добавить регресс-тест на abandoned-строку.

## 6. Модель данных (изменения models.py)

- `UserSubscription`: без новых колонок. `started_at` для queued = плановая дата старта.
- Возможное добавление: `replaced_by_subscription_id` (nullable FK) — для аналитики цепочек. По умолчанию не делаем (минимальный дизайн), можно добавить при потребности.

## 7. Открытые вопросы дизайна (Д1–Д3)

- **Д1**: при активации queued-строки кроном: считать период от планового `started_at` (окончание текущей) или от фактического момента активации? Рекомендация: от планового (`expires_at` фиксирован при покупке) — юзер видел эти даты в UX-подтверждении.
- **Д2**: статус `replaced` для старой строки при апгрейде — вводим (отличать от user-cancelled для аналитики) или оставляем `cancelled`? Рекомендация: вводим.
- **Д3**: апгрейд при уже имеющейся queued-строке — что делаем со старой queued (та же логика, что в 3.4.2: отменять и пересоздавать)?

## 8. Тесты

1. Продление того же тира при активной → queued-строка, даты по 3.2, покупка completed.
2. Апгрейд → старая replaced, новая active с перенесённым остатком дней.
3. Даунгрейд → next_subscription_tier_id на текущей, без новой строки (или queued по 3.4.2 — финализируется после Д3).
4. Пограничный: active с expires_at в прошлом → INSERT без IntegrityError.
5. Крон: expired активная + queued → активация queued, инварианты (≤1 active, ≤1 queued).
6. Идемпотентность: повторный successful_payment с тем же transaction_id → no-op.
7. find_pending_purchase не матчит abandoned.
8. UX-флоу: сообщение с датами перед инвойсом (unit на текст/кнопки).
9. Единая транзакция выдачи: activate + mark_completed атомарны.
