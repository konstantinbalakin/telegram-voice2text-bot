# Issue #140 (исходный текст)

## Баг: продление подписки падает с UNIQUE constraint на user_subscriptions.user_id — платёж сгорает

### Описание

При оплате подписки пользователем, у которого **уже есть запись в `user_subscriptions`** (активная или истёкшая), выдача товара падает:

```
CRITICAL - Payment credited but fulfillment FAILED:
error=(sqlite3.IntegrityError) UNIQUE constraint failed: user_subscriptions.user_id
[SQL: INSERT INTO user_subscriptions (user_id, tier_id, period, started_at, expires_at, ...)]
```

Деньги списаны, `successful_payment` получен, но подписка не продлевается. Покупка остаётся в исходном статусе, автоматического восстановления нет.

### Причина

`PaymentService._activate_subscription` → `SubscriptionService.create_subscription` всегда делает **INSERT** новой строки `user_subscriptions`. На таблице стоит UNIQUE constraint по `user_id` (одна строка подписки на пользователя). Повторная покупка (продление) невозможна by design текущей схемы.

Найдено при сверке БД с выпиской платёжного провайдера (март–сентябрь 2026): несколько подтверждённых succeeded-платежей за продление подписки не выданы, у пользователей сгорели оплаченные периоды. Вручную компенсировано правкой БД.

### Шаги для воспроизведения

1. Пользователь с существующей записью `user_subscriptions` (активной или expired) покупает подписку повторно
2. Платёж проходит, приходит `successful_payment`
3. `_activate_subscription` → INSERT → IntegrityError
4. `handle_successful_payment` ловит исключение, логирует CRITICAL, помечает покупку failed
5. Пользователь остаётся без продления

### Ожидаемое поведение

Повторная покупка подписки тем же пользователем должна **продлевать существующую подписку**:

- если подписка активна: `expires_at += период`
- если истекла: `expires_at = now + период`, статус → active
- покупка → completed с `provider_transaction_id` (идемпотентность)

Вариант реализации: upsert в `SubscriptionService` (обновление существующей строки вместо INSERT), либо убрать UNIQUE и вести историю подписок с одной active. Схему и миграцию обсудить отдельно.

### Сопутствующее

- `find_pending_purchase` ищет pending по user+type+item — с учётом будущих статусов (`abandoned`) убедиться, что матчинг не цепляет брошенные инвойсы.
- В `purchases.status` теперь используется значение `abandoned` (введено вручную для брошенных неоплаченных инвойсов) — его стоит добавить в `PurchaseStatus` enum, чтобы статусы не расходились между БД и кодом.

### Данные для проверки

Логи: `grep 'UNIQUE constraint failed: user_subscriptions' logs/app.log*` — инциденты июня и сентября 2026.
