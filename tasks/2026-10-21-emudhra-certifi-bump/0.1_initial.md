# Задача: закрыть eMudhra-уязвимость в образе бота (CA trust)

## Исходная формулировка К. (2026-10-21, чат)

> «Давай хвост бота доведем по процессу»

Контекст из того же чата (аудит eMudhra CA compromise от 17.10.2026):

- 8 промежуточных CA eMudhra скомпрометированы (приватные ключи P-384 подбираются мгновенно; один из ключей — число 4). Цепочки якорятся на emSign ECC Root CA - G3 и крест-подписи Sectigo/AAA.
- На kosfi аудит 21.10.2026 показал для прод-контейнера `telegram-voice2text-bot` (v0.0.79, образ собран 2026-10-10):
  - `certifi==2026.1.4` (requirements.txt) — **доверяет** фейковой цепочке;
  - системный стор контейнера `/etc/ssl/certs/ca-certificates.crt` (Debian bookworm из базового образа) — **доверяет**; именно его использует рантайм-путь бота (`REQUESTS_CA_BUNDLE=/etc/ssl/certs/ca-certificates.crt` в Dockerfile).
- Временно в работающий контейнер установлен certifi 2026.10.19 (docker exec + restart) — фикс живёт до пересоздания контейнера.
- Хост kosfi закрыт полностью (системный стор, кастомный ~/certs/combined_ca.pem, все certifi Hermes).

## Цель

Пересборка образа бота так, чтобы образ «из репозитория» не доверял скомпрометированным цепочкам eMudhra: без ручных docker exec-фиксов.

## Критерии готовности

1. В новом образе тест `https://dv-g3b-emudhra.we-have-a-problem.com/` отклоняется по обоим путям: certifi и системный стор контейнера.
2. `api.telegram.org` и рабочие интеграции бота работают без ошибок TLS.
3. Релиз/deploy штатно через `build-and-tag.yml` (изменения — не только .md, автотег ожидаем).
