# kanon-execute — реализация (R6)

Цель: закрыть задачи `plan.md` фичи в `planned`/`in-progress`.

## Выбор режима

| Режим | Когда |
|---|---|
| inline | тривиальный/сессионный план, умная модель, подписка |
| субагентный | эпик, много механических задач, API-экономика |

Важно: **итерации verify-стадии (фиксы по находкам полигона) — тоже
субагентному исполнителю** (it-фиксы — это код + тест + артефакт, полный
контекст для волны; пилот 2026-10: инлайн-итерации — соблазн «быстро
ответить оператору», ведёт к пропущенным файлам и спешным пушам).
Оркестратор в цикле итераций: бриф → верификация сырых прогонов →
чекбоксы/артефакт → коммит.

## Inline

Ближайшая незакрытая задача плана → реализация → проверка →
закрыть чекбокс → коммит `feature <fid>: <задача>`.

## Субагентный контракт (по Мореву)

**Ростер ролей** — каждый субагент со своей идентичностью, промпты в
`skills/kanon-execute/roles/` репо (путь относительно корня репо, НЕ
`<repo>/roles/`; использовать как ядро брифа при спавне):

| Роль | Файл | Когда в цикле |
|---|---|---|
| executor | roles/executor.md | волна плана: код + тесты + фикс-луп |
| test-runner | roles/test-runner.md | ПОСЛЕ каждого executor, ПЕРЕД коммитом оркестратора — механический CI-паритет, прав не имеет. Спавнь test-runner и reviewer ОДНИМ вызовом delegate_task (параллельно): оба read-only к коду, зависимости нет, последовательный спавн удваивает ожидание |
| test-fixer | roles/test-fixer.md | после test-runner, если красное: тест чинит, код — нет |
| reviewer | roles/reviewer.md | дифф волны/итерации до коммита; находит — описывает, не правит |
| doc-writer | roles/doc-writer.md | релизная стадия: docsync + whatsnew из артефактов |
| vision | roles/vision.md | скриншоты оператора, UI-ревью, alt-тексты; спавнить ТОЛЬКО на vision-провайдере (glm-5.3-flash видит, glm-5.3 — нет) |

**Модели и ограничения платформы** (проверено по докам/коду Hermes,
2026-10): `delegate_task` НЕ имеет per-task модели — все дети на
`delegation.model` из конфига (глобальный пин). Следствия:
- все дети наследуют capabilities модели из delegation.model: при
  glm-5.3-flash КАЖДЫЙ субагент ростера уже видит картинки — роль vision
  работает из коробки, ведущей модели картинки не показывай, проси
  протокол у vision-ребёнка;
- развести роли по моделям (executor потолще, runner подешевле) нельзя
  в delegate_task — либо перенастройка конфига на партию задач, либо
  Kanban (там per-task override есть: `hermes kanban create --model` /
  `set-model`) — кандидат на v2 цикла, если профиль задач вырастет.

Единица делегирования — **волна плана или связная группа задач**, не
отдельный чекбокс (чекбокс — единица плана и коммитов; делегировать его
отдельно = микроменеджмент и несобирающиеся промежуточные состояния).
Дроби волну только если она неоднородна по риску.

В массив `tasks` delegate_task — ТОЛЬКО реальные задачи: каждый элемент
спавнит ребёнка, плейсхолдер/заглушка в массиве = мусорный ребёнок,
который жрёт слот параллельности и его надо останавливать вручную.

Оркестратор НЕ пишет код волн и итераций сам (инциденты пилота: спешные
пуши и пропущенные файлы — след инлайна). Его работа: бриф (роль+контекст)
→ приём сырых отчётов → сводка оператору → чекбоксы/артефакты → коммит.
Право коммита/пуша — ТОЛЬКО у оркестратора.

- Исполнителю запрещено трактовать результаты проверок: он возвращает
  СЫРОЙ stdout тестов/команд, вывод делает оркестратор.
- «Красный» флаг test-runner на exit≠0 — не вердикт, а факт: сверяй его
  с матрицей исходов plan.md — предусмотренный планом отказ (exit 2/3
  «передай пресет явно», дрейф-стоп) и есть ожидаемый результат. Копировать
  флаг в эскалацию без сверки = ложный стоп цикла.
- Ожидания rc в бриф test-runner переписывай из матрицы plan.md, не по
  памяти оркестратора: пересказ наизусть даёт ложные «расхождения с брифом»
  в сыром отчёте и шум вместо сверки.
- Роутинг моделей: механика → дешёвая модель; дизайн/неоднозначность →
  умная. Vision-задачи (скриншоты, alt-тексты) → дешёвая видящая модель.
- Фикс-луп ≤ 5 раундов на задачу; не закрылась — стоп, эскалация оператору
  с сырыми логами (не пересказом).

**Write-early отчёт (обязательный пункт брифа любой роли)**: бриф ОБЯЗАН
требовать от субагента писать файл отчёта по ТОЧНОМУ абсолютному пути
СРАЗУ после первого результата и дополнять его по ходу работы, а не в
конце. Смысл: при смерти ребёнка (таймаут/429/context bloat) находки
выживают в файле. Подтверждено боем: verify-субагент 2026-10-15 (369с,
лог вёлся по ходу) и рецепт 12.10 (haft-fpf: чтение live-транскрипта).

**Бюджет tool-calls в брифе**: указывай явным числом ~15–20. Flash-дети
не самотормозятся и умирают на ~50 вызовах контекста — счётчик в брифе
удерживает их в рамках.

**Рецепт спасения**: ребёнок умер без файла отчёта → сначала читать
live-транскрипт
`/home/admin/.hermes/cache/delegation/live/<deleg_id>/task-N.log`
(tail — там самое ценное), и только потом решать про переспавн; слепой
переспавн теряет уже сделанную работу.

**Платформенный контекст**: `child_timeout_seconds=1800`
(config.yaml Hermes) — жёсткий лимит платформы, его не обойти;
write-early защищает от остальных смертей.

**Запрет коммитов (обязательный пункт брифа любой роли, КАПСОМ)**:
СУБАГЕНТ НЕ ДЕЛАЕТ `git commit` / `git push` / `git add`. Изменил файлы —
остановился и отчитался (какие файлы, что сделал). Право коммита/пуша —
только у оркестратора (см. выше). Решение по sandbox-защите: отклонён —
Hermes не даёт per-child прав (проверено 2026-10); защита процессная:
бриф капсом + приёмка оркестратора с `git status` перед коммитом.

## Правила

- **Стейджинг явный**: никаких `git add -A`/`git add .` без сверки `git status`
  с намерением. Слепые add ловят мусор: слепки БД, .env, артефакты сборки
  (пилот: prod-слепок 104MB уехал в публичный PR). Явный `git add <файлы>` +
  проверка `git diff --cached --stat`.
- Чекбокс закрывается ТОЛЬКО после реальной проверки (тесты прогнаны,
  `kanon check` зелёный) — не по факту написания кода.
- Один чекбокс = один коммит. Два чекбокса меняют один файл → расщепляй коммиты временной версией: сохрани полный файл вне репо, вырежи правки второй задачи (python-скриптом по точным блокам), закоммить первую + её чекбокс, верни полный файл, закоммить вторую. Слитый коммит «обе задачи сразу» ломает атомарность бисекта; git add -p по хункам ненадёжен, когда правки смежных задач легли в один хунк. Каждую промежуточную версию гони полным сьютом ДО её коммита — красная на момент коммита стадия ломает бисект молча. Стадии строй вычитанием блоков из финального файла (финал уже проверен); при стриппинге ассертуй использование (import/вызов), а не упоминание — имя модуля в докстринге не делает код зависимым.
- **Драйвер расщепления (python-скриптом) — проверенные ловушки**: (1) пинь полный финальный файл ОТДЕЛЬНОЙ копией вне репо (/tmp) и читай пин ДО любых `git checkout <commit> -- file` — чекаут для reopen чекбоксов кладёт в рабочее дерево частичную версию, и драйвер, читающий FULL из репо, прошивает заглушки во все стадии; (2) зелёный сьют ничего не доказывает, если в стадии файла собралось 0 тестов — ассертуй ОЖИДАЕМОЕ число тестов в файле перед каждым коммитом и идентичность финала эталону побайтово; (3) сегменты делай накопительными (стадия N содержит тесты 1..N), иначе коммит N молча теряет тесты предыдущих чекбоксов; (4) тесты классифицируй по ЗАВИСИМОСТЯМ (хелперы _load_*, run_init), не по тематике — тест «модуля», зовущий init-хелпер, валит стадию модуля NameError'ом; (5) в самом драйвере следи за шедоулингом — поздняя строка `FULL = read_text(...)` перетирает ранний пин; (6) историю проверяй ДО пуша (число тестов в каждом коммите: `git show <c>:<file> | grep -c 'def test'`), переигрывай через `git reset --soft`; force-push допустим только в личном непублично-разделяемом репо; (7) тикай чекбоксы plan.md по ПЕРВОМУ открытому `- [ ] `, а не по индексу из исходного списка — после каждого тика открытых боксов становится меньше, и ассерт фиксированного числа в тикере валит драйвер посреди расщепления, оставляя полустадию на диске (продолжай с той стадии, а не с нуля); (8) легитимно устаревший старый тест (поведение волны поменяло ожидание: был невалидным id, стал валидным) фиксь в КОДОВОМ коммите волны, а не в коммите новых тестов: stage-версия тестового файла = старые тесты уже с фиксой, новые тесты волны вырезаны; иначе кодовый коммит волны красный на бисекте.
- Находку ревью уровня «важно» перед фикс-раундом проверяй по посылке сам (существует ли файл/путь, на который ссылается находка, — например в research/): ревьюер ищет источники только в папке фичи и поднимает «важно» на ложном основании — фиктивный фикс-раунд тратит партию.
- Приёмка волны: сверяй `git status` с ПЛАНОМ, а не только с отчётом исполнителя — ребёнок мог поправить внеплановое (скилл, чужой файл). Легитимная по сути внеплановая правка → отдельный коммит после личной проверки содержимого, никогда в миксе с фичевыми; мусорная → откат.
- Утверждение исполнителя «падение предсуществующее» проверяй механически, не доверием: вынеси файлы волны во временную папку, перегони упавший тест без них, верни. Возврат — mv по явному пути для каждого файла: возврат по маске `mv /tmp/stash/* <одна директория>/` раскладывает тесты в директорию модулей. Подтверждённое предсуществующее падение — регуляционный долг: новый хвост в BACKLOG тем же релиз-коммитом эпика.
- Не трогай чужие фичи; изменения вне плана → сначала допиши план.
- Все задачи закрыты → `status: verify` + запись в `status-log.json` +
  коммит, дальше kanon-verify.
