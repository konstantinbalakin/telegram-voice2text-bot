# kanon-interview — интервью на юзер-сторис (R4)

Цель: превратить задачу оператора в карточку фичи `draft` для опрула.

## Правила интервью

1. До 5 вопросов за раз, один блок. Каждый вопрос — про конкретный пробел,
   не «расскажите подробнее».
2. Ответ оператора не пришёл — зафиксируй допущение (assumption) в карточке
   и пометь `assumption:` — оператор опровергнет при опруле.
3. Никаких простыней: карточка фичи ≤ 30 строк, читается в Telegram без
   скролла.

## Карточка фичи

Создай `kanon/features/<YYYYMMDD>-<category>-<slug>/feature.md`:

```markdown
---
id: <имя папки>
status: draft
title: <короткий заголовок RU>
---

# <Заголовок>

## Зачем
<1-2 предложения: боль/выгода>

## Что будет
- <наблюдаемое поведение, 3-7 пунктов>

## Не входит
- <явные границы>

## Допущения
- assumption: <если что-то не спросил>
```

И `status-log.json`: `[{"date": "<сегодня>", "status": "draft"}]`.

## Категория

epic (>1 сессии) | story (1 сессия, UX-эффект) | bug (дефект прода) |
fix (долг без UX) | docs | chore. Сомневаешься — story.

## Гейт

Перед гейтом — **прогон историй (user journey sweep)**:

Составь 4–6 конкретных историй через фичу: «у юзера есть X, он делает Y,
что он видит и получает?». Каждая — с **предложенными вариантами исходов,
один помечен рекомендацией** (с обоснованием в одну строку). Оператор
выбирает/правит — не придумывает с нуля. Примеры формата:

> История: юзер с активной подпиской покупает тот же тир.
> a) новая встанет в очередь после текущей (рекомендую: деньги не
>    сгорают, даты честные) — b) текущая продлевается сразу — c) отказ.

Формат вариантов: 2–3 на историю, короткие, с последствием для юзера
(не для кода). Истории обязаны покрывать крайние состояния: пустой
аккаунт, активная подписка, активная + что-то уже запланировано.
Не покрытая историей развилка = не спроектированная развилка.

Показ карточки оператору → его «ок» (словами или в чате) →
status: approved + коммит `feature <id>: approved`. Без ок — не двигать.
