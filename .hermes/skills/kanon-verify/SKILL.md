# kanon-verify — полигон/E2E (R7)

Цель: независимая проверка фичи в `verify` ОТДЕЛЬНЫМ агентом
(свежий контекст, не исполнитель).

## Принципы (по Мореву)

- E2E-only: гоняем пользовательские сценарии на реальном окружении
  (реальный бот/браузер/CLI), не моки.
- **Полигон гоняет ТОТ ЖЕ вход, которым пользуется юзер** — CLI-роутер
  верхнего уровня, не `python -m <внутренний модуль>`. Фикс может жить
  на одном уровне и теряться на переходе (роутер пересобирает argv для
  вложенного парсера); прямой вызов внутреннего модуля это маскирует,
  и полигон зелёный при красном pytest.
- Проверяющий не читает код реализации до прогона — сначала сценарии,
  потом (если упало) разбор.
- Сырые логи прогона сохраняются в артефакт итерации, не пересказ.

## Порядок

1. Возьми чек-лист по пресету проекта (`kanon/config.toml` → meta.preset):
   `checklists/<preset>.md` рядом с этим скиллом. Нет чек-листа —
   составь его сам по образцу chat-bot и предложи оператору.
2. Прогони каждый сценарий; результат фиксируй по сценарию:
   pass / fail + сырой лог.
3. **Упавший сценарий → сразу создай итерацию фикса** (см. kanon-iterate,
   машина честного хвоста): iterations/it-NNN/ с отчётом провала.
4. Все pass → оператору выжимка: что проверено, чем, результат.
   Его «ок» → `status: released` (whatsnew.md обязателен) + коммит.
   Если карточка уже утверждена оператором на полный автономный цикл
   (гейт был до execute) — отдельный опрул полигона НЕ создаётся: все
   pass → docsync → whatsnew → released → push, выжимка полигона идёт
   оператору вместе с релизным итогом. Гейт «его ок» — для циклов,
   где полигона был первым показом результата оператору.

## Передача оператору (обязательный формат)

Когда реализация готова и нужен опрул на полигоне:

1. **PR обязателен**: ветка запушена, PR создан (base: main). Оператор
   смотрит код в PR, не в чате.
2. **Сообщение-передача — кратко, без пересказа процесса**:
   - **Что сделано**: 3-5 строк, только суть изменений.
   - **Как проверить**: шаги на тестовом стенде, 3-6 пунктов,
     каждый — конкретное действие и ожидаемый результат.
   - Ссылка на PR. Ничего больше.
3. Доки/whatsnew догоняются позже дополнительными коммитами в тот же PR —
   это нормальный цикл, не дублировать передачу.

Отчёт субагента, ход работы, найденные по ходу сложности — НЕ входят
в сообщение-передачу (это остатётся в логах сессии).

## Правила

- **CI-паритет до пуша**: перед передачей оператору / PR прогони локально
  РОВНО те же команды, что CI (смотри .github/workflows/*), по тому же
  охвату (mypy src/ целиком, а не отдельные файлы; black только src/,
  если так делает CI; env CI, если влияет). «Я гонял пофайлово» — не
  excuse: неполный охват = не проверено.
- Не чини сам: found → итерация → kanon-iterate чинит → повторный verify
  ТОЛЬКО упавших сценариев.
- **Только прогоны и чтение**: проверяющему запрещено править файлы репо —
  ни код, ни доки, ни конфиги. Полигон — только временные каталоги
  (temp/standalone-директории вне репо). Нашёл проблему — описал в отчёте/
  итерации, правит kanon-iterate.
- Статус не двигается без полного прогона чек-листа.
